I run engineering at a consumer product that helps families preserve their memories. Boxes of VHS, VHS-C, 8mm, and MiniDV tapes arrive at the plant, get cleaned and digitized on capture rigs, and come out as video files. Before a box ships back, an inspector at a keyboard-first kiosk scans the box barcode, jumps across each digitized video, and records it as `Passed`, `Failed` (with symptoms), `Passed with exception`, or `Could not inspect`.

We built that station in four days, and it launched while I was out of the office. Over the first month, our product manager shipped 19 pull requests to that repo, most of them self-merged on green CI, while I worked on the contracts.

<Depth max={2}>

A contract here is the agreed shape of what the station sends to, or reads from, another system: the order lookup, the video files, the saved results. Green CI means every automated check on a change has passed.

</Depth>

## Ten days on the seams, four days to the floor

Our product manager wrote the requirements doc ten days before anyone touched the UI. We spent those ten days deciding which service owned each piece of state: where a box's tape list comes from, where digitized files live, where verdicts are saved so stations share history, and what triggers a recapture.

<Depth max={1}>

With the boundaries settled, I wrote a one-page brief for a coding agent on a Sunday night. One of our engineers handed it to the agent the next morning, and the station went live that Friday.

</Depth>

## What went into the brief

<Depth min={2}>

Handed a product doc with open UI choices and staging dependencies, the agent would have guessed at the boundaries and written two thousand lines of code it couldn't run.

</Depth>

The Sunday-night brief opened with two lines:

> Who this is for- [our engineer], and the coding agent [he] hands it to. Every decision in here is already made. If something reads as a choice, treat it as a bug in this document and ask rather than picking.
>
> Target- something reviewable tomorrow.

<Depth min={2}>

Then it set six rules:

1. **Standalone.** Server-rendered web app, no shared state with other front ends.
2. **Every external system behind an adapter with a mock.** Order lookup, playable media links, saved inspection records, and Slack notifications.
3. **Keep order state and media state in their own services.** The order service lists which tapes belong to a box; the media and inspection services own captured files and grading history.
4. **Runs completely on mocks with no network.** Local sample orders and bundled test videos run the station: *"That is the definition of not-blocked, and it is also how the agent verifies its own work."*
5. **No database, no auth.** Locked floor network; the inspection API is the durable record.
6. **Do not build a design system, do not pull in a component library.** On day one, we didn't know which controls would survive real boxes.

</Depth>

<Depth max={1}>

Then it set six rules. Two carry this story. Every outside system sits behind an adapter with a mock, so the whole station runs on local sample orders with no network. And no design system or component library on day one.

</Depth>

<Depth min={3}>

The brief ended with acceptance checks the agent had to run itself in mock mode: scanning sample order `1001`, grading both tapes, and checking that a failed tape blocks the order-passed notification.

Building v1 also caught a bug in my brief. I had used the playback URL as the file's ID in the saved record. While wiring the media adapter, the engineer and the agent noticed that production issues expiring signed URLs. Reopening an order an hour later, or comparing a recapture against Round 1, would see a different string for the same file. They split the contract into a permanent storage reference and a temporary playback link.

</Depth>

## How the adapters are wired

The brief named four outside systems. The station now has five ports, because the QA review page needed to read saved results back. Two face the order and media services, an order lookup and a media locator. Two face the inspection API, a sink that saves results and a reader that fetches them. The fifth is a sink for notifications. Each is an interface in one types file, with a mock and a real adapter behind it.

<ContractsPortsDiagram />

One environment variable picks the set. It defaults to mock, and anything other than the two known modes is an error. A single function builds all five adapters at once, so a station can never run a real order lookup against a mock inspection sink. Real mode has no defaults and never falls back to mock. It needs every setting filled in, and each base URL has to be a bare `https` address: no embedded credentials, no query string, no fragment. The page header prints the mode, so a station on mocks says so on screen.

The mocks keep state the way the real services do. The inspection sink appends each result to a file, once per event ID. The media mock gives every sample capture a storage version and adds one when a recapture is simulated. The notify mock appends the rendered Slack message to a log.

The real adapters share one HTTP helper. Each call has a 15-second budget that covers its retries, or 30 seconds for media. An adapter has to mark a call as repeatable before the helper will retry it, and then only after a network failure, a rate-limit response or a server error. The helper won't follow a redirect, so the bearer token is only ever sent to the host in the config. A Slack post gets one attempt, since a request that timed out may have posted anyway.

The fix for my brief's bug lives in the media port. A located file carries a permanent reference, a playback link, and a storage version when the back end reports one. A saved result keeps the reference and the version, never the link. Before each save the server checks the file again, and a refresh signs a new link for that same file or reports it missing.

</Depth>

<Depth min={5}>

The composition root and the media port, as pseudocode:

```text
adapters():
    if mode == "real": return all five real adapters
    else:              return all five mock adapters      # never a mix

locate(order, barcodes) -> per barcode, one of:
    ready       { storage reference, playback link, optional version }
    missing | ambiguous | restricted                      # kept distinct
    # if the media service itself fails, that is an error, not a "missing"

refresh(order, barcode, reference, version?):
    sign a fresh link for the same file; with a version, for that same capture
    a different file is never substituted
```

</Depth>

## Green CI for the screen, human review for the contracts

If the PM had to wait on me for every button label or shortcut change, floor fixes would take days. If an agent-written UI tweak changed an API payload, it could break real boxes at the desk. So we split the repo in the first line of the code-owners file:

> Reviewers requested automatically. No approval is required to merge; green CI is.

Green CI is required on `main`; human approval isn't. A full CI run takes about two minutes. I'm a code owner only on the adapters and CI config. Anything on the screen self-merges on green checks<Depth inline min={2}>, and every pull request has a four-box `"Station impact"` checklist: no change to the live station, needs a station update, changes what goes to an external service, or needs an upstream change first</Depth>.

<ReviewLanesDiagram />

<Depth min={4}>

The code-owners file has three rules. Our PM is requested on every change, and I'm added on the adapters directory and the CI directory. Branch protection requires the CI job and allows neither a force push nor deleting the branch. It asks for no approval.

CI is one job with five steps: install, a formatting check, the unit tests, a type check and build, then the browser tests. The job is capped at 15 minutes and the browser step at 8. Pushing again cancels the run already going, and a failed run uploads the browser report and traces.

The browser tests drive Chrome against the built bundle on a single worker. Three local servers start for them, each with a throwaway data folder: one station set up with a single inspector, one with eleven so the name picker has names to show, and one for QA review. Chrome is there because the test clips are H.264 and the Chromium that comes with the test runner can't play them. That choice cost one hung run. The runner image already ships Chrome, but the installer reinstalled it through the package manager on every run, and one of those installs stalled until the job hit its time limit. CI now installs Chrome only when it's missing, with a five-minute cap.

</Depth>

<Depth min={5}>

The review rules and the CI job, as pseudocode:

```text
code owners:
    everything            -> PM requested as reviewer
    real adapters, CI     -> PM and me requested
    a merge needs green CI and no approval

ci job (15-minute cap; pushing again cancels the current run):
    install dependencies
    check formatting
    run unit tests
    type-check and build
    install Chrome only if missing (5-minute cap)   # the runner's own Chromium can't play the test clips
    run browser tests (8-minute cap)
```

</Depth>

<Depth min={4}>

The back end keeps three rules that a second station can break. It holds a single inspection for each tape, stores any one revision of that inspection only once, and won't let a tape's round number go backwards. A save that breaks one comes back as a conflict. Before that commit the mock sink appended whatever it was handed, and one review test saved two inspections of the same tape, a state production can't hold.

The rest of the commit taught the station to live with those refusals:

- If a save went through but its reply never arrived, the station works out that it landed and keeps the result as its own.
- When the back end refuses a revision, the station drops it along with any correction waiting behind it, and takes the back end's copy.
- The Slack post for a round belongs to whichever station saved that round's last result.
- A summary for an earlier round that shows up late can't leave a newer round looking as if its summary never went out.
- A tape that joins an order partway through a round gets saved into that round once another station has reinspected it.
- When a result saved at this station is replaced by another station's, the inspector gets a warning.

The commit touched nine files, and 220 of its 387 added lines were multi-station tests.

A station reads an order back from the inspection API on every lookup and at the start of every recapture round, and the API's copy wins. When the API is unreachable, the station refuses to open an order it holds no saves for, because starting that order fresh would create a second inspection for each tape. The limits are written down in the architecture doc. One of them: when two stations save the same revision of a tape in the same millisecond, the station whose save lost takes the saved result for its own.

</Depth>

<Depth min={5}>

The mock sink after that commit, as pseudocode:

```text
record(inspection):
    saves = everything saved so far
    if this event id is already saved: return             # saved once
    tape = saves for the same order and tape
    refused = tape has a different inspection id
              or tape already has this revision
              or tape is already in a later round
    if refused: raise conflict                            # the same refusal the real back end gives
    append the record, once per event id
```

Across weeks two and three, our schedules barely overlapped. I was in and out the first two weeks, and the PM left on a planned two-week break right after. On the first Sunday of his break, I hardened the repo across six pull requests:

1. **Code owners and the pull-request template**, setting up green-CI self-merge and the `"Station impact"` checklist.
2. **A launcher that recovers on its own**, clearing a stale lock and reinstalling after an update instead of waiting for someone to fix the station by hand.
3. **Shared helpers and retired v1 fields**, tidying the client and server code without changing a byte of what the station sends.
4. **Independent browser tests**: each test makes its own order instead of sharing sample orders, and waits on real playback and seek events rather than fixed timers.
5. **Keyboard shortcuts defined in one file**, so the UI and the key listener can't drift apart.
6. **A split README**, with separate docs for engineers, whoever installs a station, and whoever runs one.

</Depth>

<Depth min={4}>

Before the launcher change, an operator cleared a leftover lock file by hand and ran the dependency install by hand after an update. Now the lock records which process holds it and when that process started. If the process is gone, or the lock is older than the computer's last boot, the lock is stale, and the launcher claims it and prints a line saying so. It also stores a hash of the dependency lockfile and reinstalls when the hash changes. A clean install deletes the installed packages first, so the launcher checks that the package registry answers within five seconds before it starts one. With no connection it keeps the old packages and tries again at the next launch.

The browser tests had shared ten sample orders, and some depended on what an earlier test had saved. One of them failed whenever it ran on its own, and repeating each test twice failed 12 of them. Each test now creates its own order through the mock lookup, which builds one from a key that says how many tapes it has. The same change removed nine fixed waits that added up to 11.1 seconds.

A unit test holds the shortcut file to the code. It loads the source of each page's key handler as text, collects every key the handler compares against, and asserts that list equals the keys the shortcut file defines. A shortcut with no handler fails, and so does a handler with no shortcut.

</Depth>

<Depth min={5}>

The launcher's stale-lock decision, as pseudocode:

```text
verdict(lock, now, booted_at):
    started = lock's recorded start time, else the file's write time
    if started is more than 5 minutes before boot: stale   # restarted; the old PID may be someone else's
    if lock records no PID:
        stale only if it was written more than 10 seconds ago
    if the PID is another running process: held
    otherwise: stale                                       # not running
```

## How a browser test counts words

The benchmark file loads each state at 1920x1080 and walks every visible text node on the page. If a dialog is open, it walks only the frontmost one. It skips screen-reader-only text, the toast, keycaps, and anything that is order data: order numbers, tape numbers, formats, names, clocks and counts. A word has to contain a letter and can't start with a digit, so `10s` and `15%` read as measurements. A visible placeholder counts. The eight symptom names have their own count, capped at two words a tile.

The same walk checks the other rules. It reads each element's computed font size and fails anything under 20 px. It flags a label when its letter spacing is over 2% of its font size, when CSS uppercases it, or when two all-caps words sit in a row. It fails any control with a keyboard shortcut and no visible keycap, and any screen that scrolls where it isn't a list. Video share is the video element's box divided by the viewport.

The budgets took three commits that Sunday. The first version of the benchmark set each budget to the count at the time: 21 for Exception, 25 for a round-two tape. The trim commit cut the copy and parked every budget at 99 while I measured, so for five hours a new word would have passed. The lock commit at 9:17 PM set each budget to its count.

Then the floor fixes moved them.

The ready screen went from 3 words to 16 because it now asks who digitized each format and tells the inspector where to find that on the label. Each raise sits in the test file next to a comment giving the reason. The video rule's arithmetic is there too: a 4:3 frame the full height of its column is 1239 by 929 pixels, 55.5% of a 1920x1080 screen.

## What the scan guard does with a barcode

Keys act as they arrive, and the guard never delays one. At the first key of a fast burst it records the state of the form. If the burst reaches four keys and then ends in Enter, the guard eats the Enter, sets the verdict, symptoms and note back to what it recorded, and shows a toast telling the inspector the scan was ignored.

Some actions can't be undone by restoring a form. Passing saves the tape, and once focus is in the note box the remaining characters of the barcode get typed into it. The station holds those two back when the key that triggers them comes in fast behind a key that isn't one of its shortcuts, such as a dash or a zero. A single fast key still acts, because simulated keys in the browser tests come in at scanner speed too. The known limit is a barcode whose first character is V: that one can still pass the tape. Order numbers are all digits, so the Enter rule handles them completely.

The guard's own browser test failed in CI, and the fix landed the next morning. The test typed its barcode with the test runner's keyboard helper. That helper sends a key only after the page has finished with the previous one, and on a slow runner the gaps grew past 30 ms. The test now dispatches each key over the browser's DevTools protocol and stamps it 8 ms after the one before, the way a real scanner's key events come with their own arrival times.

</Depth>

<Depth min={5}>

The guard's key handler, as pseudocode. The station hands the guard a way to record and restore its state, and a test for which keys are shortcuts:

```text
fast gap = 30 ms; a scan is at least 4 keys

on each key press (key, its timestamp):
    fast = it came within the gap of the previous key
    if not fast:
        start a new burst and record the station's state
    if key is Enter:
        if fast and the burst has 4 or more keys:
            put back the recorded state      # undoes what the barcode's characters changed
            report a scan                    # the station drops this Enter
        otherwise: report an ordinary key
    if key is a single character:
        count it in the burst
        the key is suspect if it was fast and an earlier key in the burst wasn't a shortcut
        if this key isn't a shortcut: remember that for the rest of the burst
    report an ordinary key
```

</Depth>
